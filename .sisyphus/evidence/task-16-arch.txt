# System Architecture

## 1. System Diagram

```
┌──────────────────────────────────────────────────────────────────┐
│  MCP Client (Claude Code / OpenCode / Cursor / Windsurf)         │
│                                                                  │
│   agent calls: ask_human() / confirm() / choose()                │
│         │                                                        │
│         ▼  stdio (JSON-RPC 2.0 over stdin/stdout)                │
├──────────────────────────────────────────────────────────────────┤
│  cardputer-hitl  (Go binary)                                     │
│  ├── main.go      — MCP server init + ServeStdio                 │
│  ├── bridge.go    — WebSocket server + state (mutex + channel)   │
│  └── tools.go     — ask_human, confirm, choose handlers          │
│         │                                                        │
│         ▼  WebSocket  ws://0.0.0.0:8765                          │
├──────────────────────────────────────────────────────────────────┤
│  Cardputer ADV firmware (Arduino / C++)                          │
│  ├── WiFi client                                                 │
│  ├── WebSocket client (auto-reconnect every 3s)                  │
│  ├── JSON parser (ArduinoJson)                                   │
│  ├── TFT renderer (per tool type)                                │
│  └── Keyboard input handler                                      │
└──────────────────────────────────────────────────────────────────┘
```

## 2. Data Flow (Happy Path)

1. **Tool Invocation**: Agent calls `ask_human(question="Which DB migration strategy?", context="3 options available")`.
2. **Request Reception**: MCP server receives call over stdio, acquires bridge mutex lock.
3. **Bridge Delivery**: Server serializes JSON payload and sends to Cardputer over WebSocket.
4. **Server Wait**: Server blocks on a Go channel waiting for reply (timeout: 300s default).
5. **Human Notification**: Cardputer beeps, renders question on TFT screen.
6. **Input Capture**: Human types answer and presses Enter.
7. **Response Transmission**: Cardputer sends raw answer string over WebSocket.
8. **Resolution**: Server receives reply, resolves channel, returns `CallToolResult` to agent.
9. **Continuation**: Agent continues execution with the answer.

## 3. Bridge Concurrency Model

The WebSocket bridge ensures atomic interactions with the following mechanisms:

- **Serialization**: A `sync.Mutex` in the `Bridge` struct serializes concurrent tool calls. Only one question can be active at a time, forcing agents to queue for human attention.
- **Dedicated Routine**: The WebSocket server runs in its own goroutine to handle connections independently of the MCP server's main loop.
- **Signal Channel**: `SendAndWait` uses a `chan string` (buffer size 1) to wait for the Cardputer's reply.
- **Connection Safety**: On disconnect mid-question, the channel is closed and an error is propagated to the agent.

## 4. Error Handling Summary

| Scenario | Server Behavior | Cardputer Behavior |
|----------|----------------|-------------------|
| Cardputer not connected | Return offline message to agent, do not error | N/A |
| Cardputer disconnects mid-question | Close pending channel, return error string to agent | Auto-reconnect loop |
| Answer timeout (300s default) | Return timeout message to agent, clear pending state | Show idle screen |
| Two agents call tools simultaneously | Second call blocks on mutex until first resolves | Not affected |
| WiFi unavailable on boot | N/A | Retries WiFi connect in loop |
| Cardputer options count out of range | Server returns MCP error before sending to device | N/A |

## 5. JSON Payload Format (Server → Cardputer)

All server-to-device communication uses JSON objects:

```json
{ "type": "ask",     "question": "...", "context": "..." }
{ "type": "confirm", "question": "...", "context": "..." }
{ "type": "choose",  "question": "...", "context": "...", "options": ["a","b","c"] }
```

**Cardputer → Server reply**: Plain UTF-8 string (the answer text or digit).
